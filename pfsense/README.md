# pfSense

pfSense CE 2.9.0, VM 100. LAN `10.0.0.1/24`, WAN `192.168.68.59`.

Quick reference: [`ips-and-network.md`](./ips-and-network.md) (all IPs/hostnames in one place) and [`secrets-links.md`](./secrets-links.md) (where to find/generate each credential used across this pfSense setup).

## DNS Resolver

**General settings:** Network Interfaces: All. Outgoing Network Interfaces: WAN only. DNSSEC enabled. Both **"Register DHCP leases"** and **"Register DHCP static mappings"** are enabled — important, these are what make `docker-host.alarconrivero.dev` etc. resolvable at all.

**Host Overrides** — see [`ips-and-network.md`](./ips-and-network.md) for the full table. Pattern used throughout:
- Externally-fronted / direct-admin services → WAN IP (`192.168.68.59`) — hairpin-NAT pattern, works whether you're home or away
- Local-only services → LAN IP (`10.0.0.1`) — routes through HAProxy's `services_frontend`

**Note:** several DNS overrides exist for services **not yet deployed** (`sonarr`, `radarr`, `prowlarr`, `bazarr`, `lidarr`, `qbittorrent`, `shelfmark`) — provisioned ahead of time, not evidence those services are live. Cross-check against [`docker-host/servarr/README.md`](../docker-host/servarr/README.md) for actual deployment status.

**Access Lists:**
| Name | Action | Network | Description |
|---|---|---|---|
| WireGuard | Allow | `10.99.0.0/30` (`tun_wg0`) | Auto-generated by pfSense's WireGuard package — do not edit/delete |
| HOME_WAN | Allow | `192.168.68.0/22` | Local Deco mesh network DNS queries |

## HAProxy

### Frontends

| Frontend | Address(es) | Cert | Default Backend |
|---|---|---|---|
| `proxmox_frontend` | `192.168.68.59:443` (WAN) | `LE-public-alarconrivero` | `proxmox_backend` |
| `services_frontend` | `10.0.0.1:443` (LAN) + `10.99.0.1:443` (WG_HETZNER) | `LE-public-alarconrivero` | none (ACL-routed) |

Both frontends share the same public Let's Encrypt cert — see [`external-access/README.md`](../external-access/README.md) for how it's issued/renewed.

`services_frontend` **Client timeout: `3600000` ms (1 hour)** — the fix for a HAProxy WebSocket-killing issue discovered while debugging Jellyfin (see [`docker-host/jellyfin/README.md`](../docker-host/jellyfin/README.md)). Applies to **every** service on this frontend, not just Jellyfin.

> 📝 **Suggestion(s) from Claude** — worth revisiting whether a blanket 1-hour timeout across the whole frontend is the right long-term call, or whether it should be scoped more narrowly per-backend, once more services are live and real-world behavior can be observed.

`proxmox_frontend` routing: ACL `pfsense_host` (Host matches `pfsense.alarconrivero.dev`) → `pfsense_backend`; default → `proxmox_backend`.

`services_frontend` routing — all ACLs use **"Host starts with"** except `ha_host` (**"Host matches"**). This inconsistency is not deliberate/standardized, just how the ACLs ended up being created — functionally fine, but a candidate for a future consistency cleanup (probably "matches" is more correct for all of them).

|---|---|---|---|---|---|---|

### WAN rules
| Source | Dest | Port | Description |
|---|---|---|---|
| Reserved/bogon | * | * | Block bogon networks |
| trusted_admin_hosts | self | 8443 | pfSense WebGUI |
| `192.168.68.0/22` | self | 443 | Routes mesh-network traffic to pfSense-routed IPs |
| `192.168.68.0/22` | self | 53 | Home network DNS to pfSense |
| trusted_admin_hosts | `10.0.0.21` | 22 | NAT SSH to docker-host |

> 📝 **Suggestion(s) from Claude** — the `192.168.68.0/22 → self:443` rule is notably broad: it allows **any device on the whole Deco mesh** to reach `services_frontend`, not just trusted-admin hosts. This is very likely intentional (it's what lets phones/TVs/laptops on the home network reach Jellyfin etc. without per-device allowlisting) — worth just confirming that's the deliberate trade-off rather than an oversight. Narrow this rule if guest Wi-Fi (if any) shares this subnet and shouldn't reach these services.

### LAN rules
Standard pfSense defaults (anti-lockout, default-allow-LAN-to-any for IPv4 and IPv6) — nothing custom.

### WG_HETZNER rules
| Source | Dest | Port | Description |
|---|---|---|---|
| `10.99.0.2` | `10.99.0.1` | ICMP echo-req | Test/diagnostic rule |
| `10.99.0.2` | `10.99.0.1` | 443 | Allow HTTPS from Hetzner to `services_frontend` — the actual traffic rule |

> 📝 **Suggestion(s) from Claude** — the ICMP test rule is labeled "TEST"; worth a conscious decision to keep it (handy for a quick tunnel-health `ping`) or remove it, rather than it sitting there indefinitely by accident.
